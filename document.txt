This document converts Razorpay’s current official Agentic Commerce track statement into a practical engineering plan: what the track means, what we should build, where AI is actually used, what remains deterministic software, how payment authorization works, how to demonstrate safety and failure handling, and how Revenue Recovery can be added later without making Phase 1 unmanageably large.

4. Our Core Project Vision
Proposed Phase 1 project:
A trusted AI commerce agent that understands a user's natural-language shopping goal, discovers products from an AI-readable merchant catalog, compares and recommends suitable products, prepares a cart and checkout, increases merchant revenue through contextual cross-sell, and executes payment only after explicit user authorization.
The system will not depend on Amazon/Flipkart scraping. We will create our own merchant catalog and expose it through controlled APIs. This makes the prototype stable, testable, reproducible and suitable for a sandbox payment flow.
5. What We Are NOT Building
We are not scraping Amazon, Flipkart, Myntra or other marketplaces as the foundation of the system.
We are not moving real customer money.
We are not giving the LLM direct database credentials.
We are not allowing the LLM to silently authorize a payment.
We are not building a general-purpose autonomous shopping agent for every website.
We are not trying to train a large language model from scratch.
We are not making every part of the system AI-powered; deterministic software should handle deterministic operations.

11. Filtering vs Ranking vs Reasoning
Hard constraints should be deterministic.
price <= 70000
Soft preferences can be used for ranking/recommendation. For example, lightweight + programming + good battery may be considered when several products satisfy the hard constraints.
The agent can then explain its recommendation:
“I recommend Product A because it satisfies your ₹70,000 budget and 16GB requirement while being lighter than the other matching options.”
We do not need to train a traditional ML model just to demonstrate this. An LLM can perform intent extraction and recommendation reasoning, while the backend enforces hard constraints.

14. End-to-End Phase 1 User Journey
User tells the agent what they want in natural language.
Agent extracts intent, hard constraints and soft preferences.
Agent calls search_products().
Backend validates the query and searches the merchant catalog.
Agent receives results and compares them.
Agent recommends one or more products with reasons.
Agent may offer one relevant cross-sell item to increase merchant revenue.
User selects a product.
Backend verifies current price and stock.
Agent creates/prepares the cart.
Backend calculates the authoritative total.
Agent presents the final amount and requests explicit payment authorization.
If user rejects, the payment request is cancelled/expired and no charge is attempted.
If user approves, backend creates the allowed test-mode payment action.
Payment status is verified.
Success produces an order confirmation.
Failure enters the controlled failure-handling path.
All important events are recorded in the audit trail.

26. Phase 2 — Revenue Recovery Extension
After Phase 1 is stable, we will add Revenue Recovery as a second capability rather than starting with two separate projects.
Revenue Recovery means detecting revenue at risk, diagnosing the reason, choosing a bounded intervention, and attempting recovery with stopping rules and an audit trail.
Razorpay's current Revenue Recovery track describes examples including payment degradation → root cause → recovery action, checkout drop-off recovery, failed-subscription recovery, B2B receivables chasing, mandate retry sequencing, Hinglish voice recovery and promise-to-pay tracking. The stated bar is measured money recovered across a batch, compliant escalation, stopping rules and an audit trail.
Our Phase 2 integration:
                 COMMERCE AGENT
Important: Revenue Recovery must not become uncontrolled payment retrying. Every intervention needs limits, authorization rules, cooldowns and a terminal stop condition.

34. Our Core Engineering Principles
AI proposes; trusted software validates and executes.
The database is the source of truth for product, price and stock.
The payment system is the source of truth for payment status.
Never trust an LLM-generated amount as the authoritative payment amount.
Financial actions require explicit authorization.
Every sensitive action is auditable.
Retries have limits and stopping conditions.
Failure handling is designed before the happy path is declared complete.
Measure the system instead of relying only on a successful demo.
Keep Phase 1 small enough to finish exceptionally well.
35. Final Mental Model
                 AGENTIC COMMERCE
One-sentence project definition
We are building a trusted AI commerce agent that turns natural-language shopping goals into controlled commerce actions: it discovers products from an AI-readable merchant catalog, reasons over user requirements, recommends and cross-sells, prepares checkout, and performs a sandbox payment only after explicit user authorization, while every financial action is bounded, explainable, auditable and failure-aware.
